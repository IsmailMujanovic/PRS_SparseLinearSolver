# Benchmark report: v2 solver against SuperLU, and v2 against v1

This document reports two comparisons for the serial complex sparse solver in this repository.

1. **v2 against SuperLU 7.0.1**, measured on one machine with the same matrix, and split into the four solver phases.
2. **v2 against v1**, derived from the two AMD uProf profiles. The v1 code was not run again; its numbers come from the existing profile.

The report was written on **2026-11-16**.

## 1. Scope and input

Both solvers read the same matrix, generated by `randomHPD(5000, 0.02, 2)` from `include/generators.hpp`. That is the case that `src/main.cpp` builds, so the numbers describe the code path that the profiles also cover.

| Item | Value |
|---|---|
| Dimension `n` | 5000 |
| Density | 0.02 |
| Seed | 2 |
| `nnz(A)` | 504,098 |
| Structure | Hermitian positive definite, complex double |

The same numbers are available as a machine-readable table in [benchmark-v2-vs-superlu.csv](benchmark-v2-vs-superlu.csv).

## 3. Part A: phase times on the M1

All values are milliseconds. The SuperLU column uses the symmetric reference configuration described in [benchmark.md](benchmark.md), section 4.1, so that its numeric phase is measured without row pivoting.

| Phase | v2 (ms) | SuperLU (ms) | v2 / SuperLU |
|---|---:|---:|---:|
| 1. Ordering | 53 | 1630 | 0.03 |
| 2. Permutation and symbolic | 169 | 1010 (estimated) | 0.17 |
| 3. Numeric factorization | 21,470 | 35,580 | 0.60 |
| 4. Triangular solution | 70 | 54 | 1.30 |
| **Total, measured median** | **22,750** | **42,030** | **0.54** |

The permutation step is 15 ms to 20 ms and is folded into phase 2 for v2. SuperLU has no public phase for it.

SuperLU's symbolic value is an estimate, not a direct timer. It is computed as `ETREE + max(0, FACT_first - FACT_reuse)`, because `zgstrf` performs the column symbolic work inside the numeric call. The estimate includes warm-cache effects.

The per-phase medians do not add up to the measured total, because run-to-run variance is about 10 percent on a laptop and the median of sums is not the sum of medians.

## 4. Part A: algorithmic quantities

Raw `nnz(L)` and raw flop counts are not directly comparable between LU and Cholesky. SuperLU computes `Pr A Pc = L U`, so it stores and reports both triangles. The project computes `PAP^H = L L^H`, so it stores one. The table therefore also gives the Cholesky-equivalent fill `(nnz(L) + nnz(U)) / 2` for SuperLU.

| Quantity | v2 | SuperLU |
|---|---:|---:|
| `nnz(A)` | 504,098 | 504,098 |
| Nonzeros stored in one triangle | 10,444,617 | 10,504,514 |
| Fill ratio, one triangle over `nnz(A)` | 20.72 | 20.84 |
| `nnz(L + U)` as SuperLU reports it | not applicable | 21,004,028 |
| Numeric flops | 1.252e11 | 2.526e11 |
| Flop ratio | 1.00 | 2.02 |
| Numeric rate | 5.92 GFLOP/s | 6.96 GFLOP/s |
| Factor storage | 159.4 MiB | 359.9 MiB |
| Peak resident set size | 749 MiB | 537 MiB |
| Forward error against the known solution | 6.1e-11 | not measured here |

### 4.1 Same-ordering comparison

Ordering quality and numeric kernel quality are separate effects. To isolate the kernel, both solvers were forced to use the same permutation.

| Ordering used | v2 numeric (s) | SuperLU numeric (s) | v2 / SuperLU |
|---|---:|---:|---:|
| v2 AMD | 21.39 | 40.46 | 0.53 |
| SuperLU MMD on `A' + A` | 21.47 | 36.27 | 0.59 |

On identical fill, the v2 kernel is 1.7 to 1.9 times faster than the SuperLU kernel. SuperLU keeps a 18 percent higher flop rate, but it performs 2.02 times the flops because LU is twice the arithmetic of Cholesky.

## 5. Part B: v1 against v2 from the uProf profiles

Shares are computed against the process total in each report, not against the sum of the listed functions.

| Function group | v1 share | v2 share |
|---|---:|---:|
| `std::_Rb_tree` and `std::set` operations | 76.58 % | 0.06 % |
| `std::complex` operators | 9.13 % | 0.12 % |
| Ordering kernel (`MD_Graph` in v1, `AMD_Graph` in v2) | 3.28 % | 0.09 % |
| `validateHPD` | 0.00 % | 56.80 % |
| `numericFactorization` | 0.47 % | 41.63 % |
| `symbolicFactorization` | 0.00 % | 0.04 % |
| `solve` | 0.00 % | 0.05 % |

| Counter | v1 | v2 |
|---|---:|---:|
| Sampled cycles | 14,959,758 | 343,922 |
| Sampled retired instructions | 13,738,873 | 996,634 |
| CPI | 1.089 | 0.345 |
| IPC | 0.92 | 2.90 |
| L1 DC misses | 1.95 % | 9.20 % |
| Branch mispredicts | 1.75 % | 0.14 % |
| Store to load conflicts, per 1000 instructions | 7.51 | 0.07 |

The ratio of sampled cycles is 43.5 and the ratio of profile durations is 40.1, so v2 is about 40 times faster end to end on that machine. The mechanism is visible in the top rows. v1 spent two thirds of its cycles inside red-black tree operations, which is the cost of storing adjacency sets as `std::set` per vertex. v2 replaces that with the bucket structure of `AMD_Graph`, and the ordering cost falls to a rounding error.

The v2 profile then exposes a different picture. Ordering is no longer visible, `validateHPD` takes 56.8 percent, and `numericFactorization` takes 41.6 percent. The high L1 miss rate in v2 is not a regression against v1, because the two percentages have different denominators, and the v1 denominator was dominated by tree traversal.

## 6. Findings

1. **v2 is faster than SuperLU at this size.** Numeric factorization is 1.7 times faster and the measured total is 1.9 times faster, on the same matrix and the same machine.
2. **Ordering is 31 times faster than SuperLU's MMD and produces the same fill.** The fill ratio differs by 0.6 percent, so the ordering quality is equal and only its cost changed.
3. **The flop advantage is algorithmic, not implementational.** Cholesky needs 1.252e11 flops and SuperLU's LU needs 2.526e11, exactly twice. Per flop, SuperLU is 18 percent faster.
4. **Peak memory is the remaining weakness.** The factor needs 159 MiB, but the process peaks at 749 MiB. The excess comes from `rowlist` in `src/numeric.cpp:20`, a `std::vector<std::vector<Entry>>` that holds 10.4 million 16-byte entries and grows by doubling, and from `L.lower.row_indices = symbolic.row_indices` at line 13, which copies a pattern that could be moved.
5. **The validation pass now dominates the profile.** Excluding it from any timed region is a precondition for a meaningful benchmark.
6. **v1 was bound by data structures, not arithmetic.** Three quarters of its cycles went to red-black tree operations, and its numeric phase was 0.47 percent of the run.

## 7. Limitations

The phase timings in Part A are machine specific. Absolute times will differ on the AMD laptop, so Part A and Part B must not be mixed in one table.

The SuperLU symbolic time is an estimate. The v1 and v2 profiles were taken on different runs and cannot be compared sample by sample, only by ratio.

Part B does not measure memory. uProf with `assess_ext` reports no allocation counters, and the report files carry none.

## 8. Defects found while measuring

1. `src/amd.cpp` is missing from `CMakeLists.txt` line 18 and from `Makefile` line 77. The `program` target therefore fails to link with an undefined reference to `AMD(Matrix const&)`.
2. `benchmark/bench_superlu.cpp` calls `MD(A)` in `runOurSolver`, while `src/main.cpp` calls `AMD(A)`. The benchmark therefore measures the v1 ordering kernel and never exercises v2. A run of `./build/bench --random 5000:0.02:2` did not finish within 420 seconds for this reason, while the v2 path finishes in 21 seconds.

## 9. Reproduction

Part A was produced with two small drivers kept outside the repository, built against `build/libprs_solver.a`, `src/amd.cpp`, and `benchmark/superlu_adapter.cpp`.

```bash
c++ -O2 -std=c++17 -Iinclude -Ibenchmark probe_ours.cpp src/amd.cpp build/libprs_solver.a -o probe_ours
c++ -O2 -std=c++17 -Iinclude -Ibenchmark -I/opt/homebrew/include \
    probe_slu.cpp benchmark/superlu_adapter.cpp build/libprs_solver.a \
    -L/opt/homebrew/lib -lsuperlu -o probe_slu

OPENBLAS_NUM_THREADS=1 ./probe_ours 5000 0.02 2 AMD
OPENBLAS_NUM_THREADS=1 ./probe_slu  5000 0.02 2 1 3
```

Part B reads the two existing report files, `profiles/v1_clean_report.csv` and `profiles/v2_clean_report.csv`, in the `HOTTEST FUNCTIONS` and `HOTTEST PROCESSES` sections.
